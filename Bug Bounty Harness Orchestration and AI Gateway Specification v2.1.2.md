# Bug Bounty Harness Orchestration and AI Gateway Specification v2.1.2

## Overview

This document describes the current orchestration of the Autonomous Bug Bounty Harness, how core components interact during a hunt, and the AI model gateways required to operate the system efficiently and safely. It also defines technical specifications and cost-aware model routing for local and remote LLM backends, forming a blueprint for completing remaining implementation phases. As of v2.1.2, the specification incorporates Qwen3.8-27B-Uncensored-HauhauCS-Aggressive-MTP as a LOCAL_HEAVY backend, refining the model-routing tier structure and adding cloud GPU deployment profiles for on-demand 27B inference.[^1][^2][^3][^4][^7]

## Harness Orchestration

### Control Plane and Primary Interfaces

The harness is organized around a Python control plane with a single orchestration brain (`orchestrator/admiral.py`) and a TypeScript/Node war room UI (`T3MP3ST`). T3MP3ST exposes the operator interface on port 3333 and communicates with OpAdmiral via REST and a single client-initiated WebSocket on port 8001.[^2][^3]

OpAdmiral is responsible for task creation, specialist dispatch, token budget tracking, and event streaming to the UI. All shared types, config, and event bus abstractions live in `core/` and are imported by orchestrator, budget, triage, compliance, sessions, and specialist modules.[^5][^4][^2]

### Memory, Compliance, and Outbound Traffic

The `mempalace` service provides long-term memory, FP pattern storage, scope and taxonomy tables, and vector similarity search, and is exposed on port 8000 as an MCP/HTTP service. All outbound HTTP traffic from fuzzers, scanners, Playwright, and LLM-assisted tools is routed through a mitmproxy-based egress proxy (`compliance/egress_proxy.py`) listening on port 8080.[^6][^3][^4][^2]

Scope enforcement logic resides in `compliance/scope_gate.py` and is invoked by the egress proxy on each request, applying exact, wildcard, CIDR, and regex rules plus DNS rebinding protection before packets leave the machine. A single source of truth for headers and rate limits is maintained in `platform_profile.json` under each workspace, generated by `header_injector.py` during `main.py init`.[^4][^6][^2]

Out-of-band (OOB) callbacks are handled by `compliance/oob_engine.py`, which integrates with public or self-hosted Interactsh depending on `INTERACTSH_MODE`; OOB status is surfaced to the war room via OpAdmiral events.[^6][^2]

### Specialist Swarm and External Tools

Sixteen Python specialist agents implement the vulnerability categories (SQLi, XSS, SSRF, IDOR, LFI, RCE, XXE, JWT, Open Redirect, Prototype Pollution, CSTI, Mass Assignment, Header Injection, BAC, AI Jailbreak, Business Logic). These share a common base (`agents/specialist_base.py`) that wires mempalace FP checks, dual-session testing for IDOR/BAC, and OOB mixing.[^4]

Specialists receive tasks from OpAdmiral, use ModelRouter to call appropriate LLM backends, and emit findings and orchestration events onto the InMemoryEventBus. External tools—`adhd` (divergent ideation), `claude-bug-bounty` (ReAct scanner), `jsleak` (JS secret scanner), and `Agent-Reach` (OSINT daemon)—operate as separate processes that integrate via HTTP, MCP, and environment variables.[^3][^5][^4]

`adhd` runs as a Node CLI, consuming security-specific cognitive frames and calling LLMs via a client that is being adapted to route through OpAdmiral for token tracking and FP anti-pattern checks via mempalace. `claude-bug-bounty` coordinates classic recon and scanning tools (subfinder, katana, nuclei, dalfox, etc.) and is being retrofitted to route its LLM calls to ModelRouter and send potential findings back to OpAdmiral via `/api/triage/callback`.[^3][^4]

### Workflow Stages and Component Interactions

The end-to-end hunt is defined across twelve phases: scope parsing, recon & discovery, attack planning, payload generation, JS/code analysis, fuzzing, response analysis, FP filtering, validation, chain discovery, triage, and report generation. Scope parsing uses pure Python for CSV/JSON ingestion plus limited LLM help for ambiguous human scope text, feeding ScopeGate and platform_profile.json.[^1][^2]

Recon and discovery rely on external CLI tools and jsleak, with LLM assistance only for prioritizing endpoints. Attack planning uses `adhd` with local and Groq-hosted models, cross-checking FP patterns in mempalace before moving forward. When a LOCAL_HEAVY backend (Qwen3.8-27B) is available, deep divergent brainstorming and WAF evasion planning preferentially route to it over Groq 70B.[^1][^3][^4][^7]

Payload generation and response analysis are handled mainly by the 12 code-oriented specialists. LOCAL_LIGHT models (Qwen coder 7B) handle routine payloads, while LOCAL_HEAVY (Qwen3.8-27B Aggressive) handles complex polyglot payloads, multi-layer chains, and deep dataflow analysis when available; Groq 70B serves as the fallback for heavy reasoning. Validation, chain discovery, and triage rely more heavily on Groq or premium APIs for deep reasoning and narrative construction, with reporting delegated to `reporting/taxonomy.py` and downstream templates.[^2][^4][^1][^7]

## AI Gateways and Model Routing

### Model Tiers and Backends

The harness defines four effective gateway categories aligned with cost, capability, and deployment topology:[^6][^1][^7]

1. **LOCAL_LIGHT** — Laptop Ollama models (3–8B) for cheap classification, basic payloads, and high-volume noise filtering. Assumes RTX 4050 6 GB VRAM, loading one model at a time. Supported models: Qwen 2.5 coder 7B, Llama 3.1 8B, Mistral 7B, Qwen 2.5 coder 3B at Q4 quantization.
2. **LOCAL_HEAVY** — Qwen3.8-27B-Uncensored-HauhauCS-Aggressive-MTP served via `llama-server` with FastMTP acceleration on a workstation GPU (24–48 GB VRAM) or on-demand cloud GPU (RTX 4090 / L40S). Used for deep offensive reasoning, complex payload generation, exploit chain synthesis, and AI jailbreak flows where uncensored output is critical.
3. **PAID_FREE** — Free-but-metered APIs (primarily Groq), offering Llama 3.1 70B, 8B instant, Mixtral 8x7B, and Gemma2 9B with rate limits around 30 RPM and token budgets per minute.
4. **PAID_PREMIUM** — GPT-4o/4o-mini from OpenAI and Claude Sonnet/Haiku from Anthropic, with per-million-token pricing; only acceptable for confirmed findings, final CVSS reasoning, and report writing.

LOCAL_LIGHT and LOCAL_HEAVY share the `LOCAL` tier conceptually but differ in endpoint and applicable tasks. LOCAL_HEAVY is reserved for tasks that benefit from uncensored deep reasoning and can tolerate slower generation relative to Groq's hosted 70B, while LOCAL_LIGHT remains the default for high-volume classification.[^7]

ModelRouter in `budget/model_router.py` encapsulates all four categories, providing a routing table that maps discrete harness tasks to a tier and model name, plus failover logic. A new `LOCAL_HEAVY` internal flag distinguishes laptop-scale models from 27B-scale deployments.[^4][^1][^7]

### Qwen3.8-27B Aggressive FastMTP Profile

Qwen3.8-27B is a 27B-parameter causal language model with native text, image, and video capabilities, released under Apache 2.0 and further uncensored by HauhauCS with an "Aggressive" profile (0 refusals). The Aggressive MTP GGUF release preserves Qwen3.8's native NextN/embedded-MTP heads and adds a HauhauCS FastMTP sidecar for acceleration across all text quantizations.[^7]

The text quantizations relevant to the harness are:

- Q4_K_P: 17.92 GB GGUF, approximate 5.25 BPW.
- Q3_K_P: 13.44 GB GGUF.
- IQ4_XS and IQ3_M/Xs: 12–15.7 GB GGUF range.

A separate BF16 mmproj projector (931 MB) enables vision, and a FastMTP 32K sidecar (903 MB) is used to accelerate text generation. HauhauCS FastMTP provides up to 3.02× document TG and 1.93× reasoning TG versus non-MTP, with all drafted tokens verified by the target model.[^7]

The recommended thinking-mode parameters are temperature 1.0, top-p 0.95, top-k 20, no presence penalty, repetition penalty 1.0, with reasoning-effort set to `xhigh` for deepest chains. The runtime is `llama-server` with HauhauCS FastMTP patch, serving in OpenAI-compatible mode. Recommended flags include `--spec-draft-model` for the FastMTP-32K sidecar, `--spec-type draft-mtp`, `--spec-draft-n-max 3`, `--reasoning on`, and `--jinja`.[^7]

### Task-to-Model Allocation

For scope parsing and header generation, most tasks use pure Python, with ambiguous scope interpretation routed to Groq Llama 70B and regex generation routed to local Qwen coder. Recon and JS secret scanning are mostly tool-driven and do not require LLMs; endpoint prioritization uses LOCAL_LIGHT Qwen coder for cheap classification.[^1]

Attack planning uses a split: shallow frame ideation runs on LOCAL_LIGHT Llama 3.1 8B for speed. Deep divergent brainstorming, WAF evasion planning, and uncensored offensive strategy route primarily to LOCAL_HEAVY (Qwen3.8-27B Aggressive) when available, with Groq Llama 3.1 70B as the fallback. FP anti-pattern checks use very small LOCAL_LIGHT Qwen coder 3B plus mempalace to minimize cost.[^3][^4][^1][^7]

Payload generation for SQLi, XSS, SSRF, LFI, RCE, XXE, JWT, Open Redirect, Prototype Pollution, CSTI, Header Injection, and many OOB payloads is routed primarily to LOCAL_LIGHT Qwen coder 7B for routine cases. Complex payload composition (polyglots, multi-layer chains) and deep dataflow analysis route to LOCAL_HEAVY (Qwen3.8-27B Aggressive) when available, falling back to Groq 70B.[^4][^1][^7]

Response analysis and FP filtering rely on LOCAL_LIGHT models (Qwen coder 3B, Mistral 7B, Llama 8B) for bulk error classification and noise filtering, with LOCAL_HEAVY reserved for ambiguous or high-impact findings. Validation, AI jailbreak confirmation (primary: LOCAL_HEAVY for crafting and testing jailbreak payloads), business logic analysis, chain discovery, impact escalation, CVSS vector calculation, and dispute preparation are mainly on Groq 70B, with LOCAL_HEAVY used for exploit-centric chain construction where uncensored exploration is needed, and occasional escalation to Claude Sonnet or GPT-4o for premium reasoning and report wording.[^1][^4][^7]

Illustrative routing changes (v2.1.2):

- `ideation_deep` (Phase ③): Primary → `qwen3.8-27b-aggressive-q4-local` (LOCAL_HEAVY); Fallback → Groq Llama 3.1 70B.
- `payload_polyglot` (Phase ④): Primary → LOCAL_HEAVY; Fallback → Groq 70B.
- `chain_analysis` / `impact_escalation` (Phase ⑩): Primary → Groq 70B; Optional → LOCAL_HEAVY for exploit-centric chains.
- `ai_jailbreak_confirm`: Primary → LOCAL_HEAVY; Fallback → Groq 70B + GPT-4o-mini.

### Budget and Fallback Logic

`budget/token_tracker.py` tracks token usage per agent and per tier, applying warning thresholds and hard caps, and emitting events to OpAdmiral when budgets approach exhaustion. The routing guide encodes per-task token expectations so that LOCAL_LIGHT, LOCAL_HEAVY, and PAID_FREE tiers absorb most load during exploratory phases, with PAID_PREMIUM used strictly post-triage.[^4][^1]

TokenTracker must gain awareness of LOCAL_HEAVY usage as a separate bucket so that GPU-hours and inference load can be monitored and optionally billed or cost-shared. New events such as `local_heavy_usage` can be emitted to T3MP3ST, showing how often Qwen3.8-27B is invoked and how many tasks route to it versus Groq or laptop-local models.[^7]

Ollama health checks run at startup; if local models are unavailable or no tags are loaded, ModelRouter promotes LOCAL_LIGHT tasks to PAID_FREE (Groq 70B) and logs a warning. Startup health checks also probe `local_heavy_url` alongside `ollama_url` and Groq, emitting warnings in logs and the war room when Qwen3.8-27B is offline. If both LOCAL endpoints and PAID_FREE backends fail (e.g., missing Groq API key), the harness refuses to start and prints a clear error indicating no model backend is configured.[^2][^4][^7]

Token budgets and `max_session_cost_usd` are defined in `HarnessConfig` and used to compute allowable usage window per engagement (e.g., a 10 USD cap), which is surfaced visually in T3MP3ST's token budget gauge and used by OpAdmiral to throttle deep reasoning calls. HarnessConfig gains additional fields for LOCAL_HEAVY: `local_heavy_enabled: bool`, `local_heavy_url: str` (llama-server endpoint), and `local_heavy_hourly_cost: float` (for cloud GPU sessions), allowing OpAdmiral to make cost-aware routing decisions.[^5][^3][^7]

## Cost-Aware Gateway Combinations

### Baseline Laptop Profile (Current Hardware)

On the current Ryzen 5 + 16 GB RAM + RTX 4050 laptop, LOCAL_LIGHT tier is limited to one 7–8B model at a time with 6 GB VRAM, which constrains deep reasoning and chain analysis. LOCAL_HEAVY is not available in this profile. Under this profile, the most cost-effective combination is:[^6][^1]

- LOCAL_LIGHT: Qwen 2.5 coder 7B and Llama 3.1 8B for payloads and light reasoning.
- PAID_FREE: Groq Llama 3.1 70B for complex tasks (attack planning, validation, chains).
- PAID_PREMIUM: GPT-4o-mini or Claude Haiku used rarely for FP disputes or report polishing.

Infrastructure specs estimate monthly spend between 0 and 10 USD when relying primarily on Groq free tier and occasional GPT-4o validation in this baseline profile. This combination keeps recon, payload crafting, and most FP filtering effectively free while still offering frontier-level reasoning when required.[^6][^1]

### Dedicated Workstation and Local 27B Models (Profile E)

The dedicated workstation profile assumes 64–128 GB RAM and a 24–48 GB GPU (RTX 4090 or A6000), enabling Qwen3.8-27B Aggressive at Q4_K_P (17.92 GB GGUF) with FastMTP-32K sidecar (903 MB). In that profile, LOCAL_HEAVY covers most exploit reasoning, deep offensive brainstorming, and complex payload generation, relegating Groq 70B and premium APIs to only the most complex chains or report generation.[^6][^7]

Gateway wiring in this profile:

- `llama-server` hosts Q4_K_P + FastMTP on `http://127.0.0.1:8080` or a dedicated port.
- `HarnessConfig` sets `local_heavy_enabled = true` and `local_heavy_url` to the llama-server endpoint.
- ModelRouter maps `LOCAL_HEAVY` tasks to this endpoint.
- Context is configured to 8k–32k tokens to match exploit-hunt workflows and avoid KV cache exhaustion.

Cost is primarily upfront hardware (~1,200–3,000 USD for GPU and RAM) with ongoing electricity only; no per-token charges. This profile significantly reduces reliance on Groq 70B in phases ③–⑩.[^6][^7]

### Cloud GPU Bursting Profile (Profile F)

Profile F uses on-demand cloud GPUs (RunPod, Vast.ai, Lambda) hosting Qwen3.8-27B Aggressive for limited time-windows during hunts. The laptop retains the control plane, mempalace, and LOCAL_LIGHT models, while LOCAL_HEAVY endpoints are switched to the cloud instance URL.[^6][^7]

Hardware (cloud):

- RTX 4090 (24 GB) or L40S (48 GB) on RunPod/Vast/Lambda.
- Text quant: Q4_K_P + FastMTP-32K sidecar.
- Context: 8k–16k (4090) or 32k–64k (L40S).

Gateway wiring:

- `llama-server` listens on a public or VPN-exposed address; OpAdmiral and ModelRouter use its URL as the LOCAL_HEAVY endpoint.
- Egress proxy rules must treat calls to this endpoint as internal (no scope enforcement), while all target traffic continues through compliance proxy.

A typical burst session costs ~0.35 USD/hr (4090) to ~0.79 USD/hr (L40S), yielding ~2.8–6.3 USD for an 8-hour intensive hunt. ModelRouter is configured to fall back to Groq 70B when the cloud endpoint is offline.[^6][^7]

This profile adds a pay-per-hour heavy LOCAL backend for select hunts without permanent hardware investment, suitable when a single large-scope program requires more reasoning capacity than the laptop's LOCAL_LIGHT tier can provide, and when the expected bounty makes a 10–30 USD compute spend reasonable.[^1][^6][^7]

### Legacy Cloud GPU Profile (Profile D)

Profile D in the infrastructure spec uses on-demand cloud GPUs for general model hosting (e.g., Llama 3.1 70B or smaller Qwen models). Profile F supersedes Profile D for Qwen3.8-27B workloads but Profile D remains valid for non-27B cloud GPU scenarios.[^6]

## Main AI Gateways Required

### Gateway Types

The harness requires the following AI gateway categories:

1. **LOCAL_LIGHT inference gateway** (Ollama or llama-server) for models in the 3–8B range on laptop GPU.
2. **LOCAL_HEAVY inference gateway** (`llama-server` with HauhauCS FastMTP) for Qwen3.8-27B Aggressive on workstation or cloud GPU — serving in OpenAI-compatible mode with `--spec-draft-model`, `--spec-type draft-mtp`, `--spec-draft-n-max 3`, `--reasoning on`, and `--jinja` flags.
3. **Free API gateway** (Groq) for 70B models with rate limits, used as PAID_FREE.
4. **Premium API gateway** (OpenAI, Anthropic) for high-end reasoning and report writing, used sparsely.

Environment variables and configuration fields in `HarnessConfig` encode URLs and API keys for these gateways (`ollama_url`, `local_heavy_url`, `local_heavy_enabled`, `local_heavy_hourly_cost`, `groq_api_key`, plus provider-specific keys for premium models). ModelRouter abstracts these gateways behind a per-task routing table, so specialists and external tools never call providers directly.[^5][^4][^1][^7]

### Gateway Combinations and Trade-offs

A minimal combination that satisfies all current design goals (no LOCAL_HEAVY hardware) is:

- LOCAL_LIGHT: Ollama on laptop with Qwen coder 7B and Llama 3.1 8B.
- PAID_FREE: Groq Llama 3.1 70B.
- PAID_PREMIUM: One provider (OpenAI or Anthropic) with a single primary model (GPT-4o or Claude Sonnet).

This combination keeps monthly cost very low while still enabling attack planning, payload generation, FP filtering, validation, chain analysis, and report generation across all phases.[^1][^6]

The recommended expanded combination for workstation or cloud GPU scenarios (with Qwen3.8-27B) is:

- LOCAL_LIGHT: Qwen 2.5 coder 7B and Llama 3.1 8B on laptop Ollama for classification and routine payloads.
- LOCAL_HEAVY: Qwen3.8-27B Aggressive Q4_K_P + FastMTP on workstation/cloud GPU for deep offensive reasoning, complex payloads, exploit chains, and AI jailbreak flows.
- PAID_FREE: Groq 70B reserved mostly for business logic, general triage, and fallback for LOCAL_HEAVY tasks.
- PAID_PREMIUM: Claude Sonnet for security narrative, complex chains, and report polishing.

This expanded combination reduces dependence on Groq for exploit reasoning and lowers token usage on premium tiers, at the expense of GPU hardware purchase or cloud rental.[^1][^6][^7]

## Integration Considerations

### Security and Compliance

Qwen3.8-27B Aggressive is explicitly uncensored, which increases the risk of generating payloads or strategies that could violate program rules if applied out-of-scope. Therefore:

- All HTTP requests produced as a result of LOCAL_HEAVY planning must still pass through `compliance/egress_proxy.py` and ScopeGate.
- AI jailbreak and offensive payload specialists using this backend must be constrained to in-scope assets and targets as defined in `TargetScope` and platform_profile.json.

The harness does not allow direct network access from the model runtime to targets; Qwen3.8-27B integration adds reasoning power, not new network surfaces, which preserves compliance invariants.[^7]

### Observability and Budgeting

TokenTracker must gain awareness of LOCAL_HEAVY usage as a separate bucket so that GPU-hours and inference load can be monitored and optionally billed or cost-shared. New events such as `local_heavy_usage` are emitted to T3MP3ST, showing how often Qwen3.8-27B is invoked and how many tasks route to it versus Groq or laptop-local models.[^7]

## Remaining Gaps and Blueprint Actions

### Specialist and Tool Integration Gaps

Phase 4B lists several outstanding integration steps: `adhd/src/engine.ts` needs token reporting and FP anti-pattern queries; `claude-bug-bounty` agent, engine, and brain modules must be wired to ModelRouter, egress proxy, and mempalace; jsleak must honor HTTP proxy and output JSON.[^4]

Completing these tweaks ensures that all external tools participate fully in token tracking, scope enforcement, and memory sharing, aligning their behavior with the rest of the harness. It also centralizes model usage behind OpAdmiral and ModelRouter, preventing tools from bypassing budget rules.[^2][^4]

### Orchestration, Reporting, and UI Gaps

Phase 5 is not yet implemented and covers `reporting/taxonomy.py`, `orchestrator/admiral.py`, `main.py`, and T3MP3ST wiring. Implementing admiral with REST and WebSocket endpoints, plus startup wiring for TokenTracker, ModelRouter, SessionManager, ScopeGate, mempalace, and egress proxy, will bring the harness together into a cohesive system.[^5][^2][^4]

Reporting taxonomy must be implemented to provide VRT, CWE, CVSS, and report templates for HackerOne, Bugcrowd, and other platforms, using LLM backends only where necessary for wording and justification. T3MP3ST server and docs must be updated to consume admiral APIs, display token budgets (including LOCAL_HEAVY GPU-hour gauges), FP reasons, OOB badges, and support confirm/reject workflows.[^3][^2][^4][^7]

### Validation and Dry-Run Test Harness

Phase 6 requires a `tests` package with unit tests for ScopeGate, OSINT exemption, taxonomy mappings, and end-to-end dry-run flows. Establishing these tests will validate that scope enforcement, OSINT handling, report classification, and dry-run semantics match design, and will serve as regression safety nets.[^2][^4]

### Qwen3.8-27B Integration Steps

The blueprint to complete Qwen3.8-27B integration is:[^7]

1. **Deploy llama-server with Q4_K_P + FastMTP** on either workstation or cloud GPU, exposing an OpenAI-compatible HTTP endpoint.
2. **Extend HarnessConfig and ModelRouter** to recognize a `LOCAL_HEAVY` endpoint and update routing entries for deep offensive reasoning tasks (`ideation_deep`, `payload_polyglot`, `chain_analysis`, `ai_jailbreak_confirm`).
3. **Update TokenTracker and T3MP3ST** to display LOCAL_HEAVY usage, GPU-hour estimates, and budget impact.
4. **Ensure egress proxy and ScopeGate invariants** remain unchanged; Qwen3.8-27B must not bypass compliance layers.
5. **Document cost models** for workstation and cloud GPU deployments using the infrastructure and cloud pricing specs to decide when to enable or disable LOCAL_HEAVY per engagement.

### Blueprint Summary

The blueprint to bridge remaining gaps is:

1. Finish Phase 4B integrations so all external tools route LLM calls via ModelRouter, respect egress proxy, and use mempalace.[^4]
2. Implement Phase 5 orchestrator, reporting, and UI wiring around OpAdmiral, making `main.py run` spin up egress proxy, mempalace, admiral, sessions, and war room in sequence.[^2][^4]
3. Implement Phase 6 tests for compliance and taxonomy, plus dry-run harness.[^4]
4. Refine ModelRouter configuration for current and future AI gateways (LOCAL_LIGHT laptop, LOCAL_HEAVY Qwen3.8-27B workstation/cloud, Groq free tier, premium APIs), keeping budgets and caps aligned with `HarnessConfig`.
5. Complete Qwen3.8-27B integration steps (deploy llama-server, extend HarnessConfig/ModelRouter, update TokenTracker/T3MP3ST, verify compliance invariants, document cost models).[^7]

This specification, combined with existing design, routing, and implementation guides, provides a clear blueprint for finishing the harness and scaling AI gateways in a cost-aware manner.[^4][^6][^1][^7]
